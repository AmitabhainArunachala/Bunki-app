# SRS Technical Audit — 回廊 KAIRO review engine (2026-08-11)

**Engine:** FSRS-6 via `ts-fsrs` v5.4.1, vendored at
`prototypes/corridor/vendor/ts-fsrs.mjs` (1,869 lines), driven by pinned
parameters in `prototypes/corridor/data/fsrs-pin.json`. All app-side scheduling
code is in `prototypes/corridor/corridor.js`. Every number in this audit comes
from executing the shipped code with the shipped parameters, including the
exact localStorage serialize/revive round-trip a real card undergoes.

Pinned parameters: request retention **0.90**, maximum interval **36,500 d**,
fuzz **disabled**, short-term scheduling **enabled**, learning steps
`["1m","10m"]`, relearning steps `["10m"]`, weight set
`bunki-fsrs6-r090-defaults-v1` (the FSRS-6 population defaults).

---

## 1 · Core algorithm

**Algorithm:** FSRS-6 (not SM-2). There is no Ease Factor — FSRS replaces it
with two continuous memory variables per card: **Stability S** (days until
recall probability decays to 90%) and **Difficulty D ∈ [1,10]**.

### 1A. The actual code

App side (`corridor.js`):

```js
const srsKey = (t, id) => `${t}:${id}`;
function srsCardOf(item, now) {
  const rec = S.srs[srsKey(item.t, item.id)];
  if (!rec) return fsrsApi.createEmptyCard(now);
  const c = { ...rec, due: new Date(rec.due) };
  if (rec.last_review) c.last_review = new Date(rec.last_review);
  return c;
}
function srsStore(item, card) {
  S.srs[srsKey(item.t, item.id)] = {
    ...card,
    due: card.due.toISOString(),
    last_review: card.last_review ? card.last_review.toISOString() : undefined,
  };
  saveStore();
}
```

The grade handler (inside `renderReview`) — one `repeat()` call computes all
four futures, the pressed one is stored:

```js
const card = srsCardOf(item, now);
const result = scheduler.repeat(card, now);
// per button: result[fsrsApi.Rating[rating]].card  → srsStore(item, …)
```

The engine's formulas (verbatim from the vendored `ts-fsrs.mjs`):

```js
// Retrievability (power forgetting curve):
function forgetting_curve(decayOrParams, elapsed_days, stability) {
  const { decay, factor } = computeDecayFactor(decayOrParams);
  return roundTo(Math.pow(1 + factor * elapsed_days / stability, decay), 8);
}
// Interval from stability at request_retention 0.9:
next_interval(s, elapsed_days) {
  const newInterval = Math.min(Math.max(1, Math.round(s * this.intervalModifier)),
    this.param.maximum_interval);
  return this.apply_fuzz(newInterval, elapsed_days);   // fuzz disabled → identity
}
// Difficulty update (linear damping + mean reversion toward D0(Easy)):
next_difficulty(d, g) {
  const delta_d = -this.param.w[6] * (g - 3);
  const next_d = d + this.linear_damping(delta_d, d);  // delta_d * (10-d)/9
  return clamp(this.mean_reversion(this.init_difficulty(Rating.Easy), next_d), 1, 10);
}
// Stability after successful recall (w15 = Hard penalty, w16 = Easy bonus):
next_recall_stability(d, s, r, g) {
  const hard_penalty = Rating.Hard === g ? w[15] : 1;
  const easy_bound  = Rating.Easy === g ? w[16] : 1;
  return clamp(s * (1 + Math.exp(w[8]) * (11 - d) * Math.pow(s, -w[9])
    * (Math.exp((1 - r) * w[10]) - 1) * hard_penalty * easy_bound), S_MIN, 36500);
}
// Stability after a lapse:
next_forget_stability(d, s, r) {
  return clamp(w[11] * Math.pow(d, -w[12]) * (Math.pow(s + 1, w[13]) - 1)
    * Math.exp((1 - r) * w[14]), S_MIN, 36500);
}
```

### 1B. Learning steps vs review intervals

Learning/relearning state machine (`BasicLearningStepsStrategy`, verbatim
behavior): while a card is in Learning and hasn't exhausted `["1m","10m"]`:

- **Again** → back to step 0 (1 min)
- **Hard** → mean of steps 1 and 2 = **6 min** (this is where the 6-minute
  Hard label comes from)
- **Good** → next step (10 min), then graduation to Review
- **Easy** → skips straight to Review with the Easy initial stability

A lapse from Review enters Relearning at the 10-min step. **Again on a Review
card always means relearning** — never an interval multiply.

### 1C. Graduating / easy interval

Not fixed constants as in Anki — computed from initial stability
`init_stability(g) = w[g-1]`, so S₀ = 0.212 / 1.293 / 2.307 / 8.296 for
Again/Hard/Good/Easy. With this weight set graduation lands at **2 d** (Good)
and initial **Easy = 8 d**.

### 1D. Due dates, day boundaries, timezone

Due is an exact UTC timestamp (ISO string in storage); queue admission is
`new Date(rec.due) <= now` — no day bucketing, no Anki-style 4 a.m. rollover.
Display bucketing (今日/明日) is by the device's **local midnight** (fixed
2026-08-11: cards due later today previously displayed as 明日). Sub-day
intervals are real minutes; day intervals land at the same clock time N days
later.

## 2 · Full lifecycle (executed, through the storage round-trip)

```
t+0      NEW                        → shown: Again 1min · Hard 6min · Good 10min · Easy 8d
t+0      Good  → Learning  10min   S=2.31   D=2.12  reps=1
t+10min  Good  → Review    2d      S=2.31   D=2.11  reps=2   (graduates)
due day  Good  → Review    11d     S=10.97  D=2.10  reps=3
due day  Hard  → Review    32d     S=32.23  D=4.74  reps=4   (see note below)
due day  Again → Relearn.  10min   S=2.40   D=8.26  lapses=1 (S collapsed 32.23→2.40, D 4.74→8.26)
+10min   Good  → Review    2d      S=2.40   D=8.24            (re-graduates)
review 1 Good  → 5d    S=5.10     review 2 Good → 11d   S=10.81
review 3 Good  → 22d   S=21.85    review 4 Good → 42d   S=41.62
review 5 Good  → 76d   S=75.67    review 6 Good → 132d  S=131.77
```

Post-lapse growth is visibly slower than pre-lapse (D=8.2 vs 2.1 damps the
S-growth term `(11−D)`) — the FSRS-intended behavior.

**Note on Hard:** Hard _on the due day_ grows the interval (32 d from 11 d)
because the card survived the full interval; Hard means "recalled with
effort," not "shrink the interval." This is correct FSRS and differs from
SM-2 intuition.

## 3 · Edge cases (executed)

**Long absence** (7d-stable card, 90 days overdue, retrievability R = 70.1%):

| Button | Result                                                 |
| ------ | ------------------------------------------------------ |
| Again  | Relearning 10 min (S 10.97 → 2.14, D → 7.39, lapses+1) |
| Hard   | Review 80 d                                            |
| Good   | Review **125 d**                                       |
| Easy   | Review 225 d                                           |

Surviving a long gap earns large stability — correct FSRS; no "overdue
penalty," no interval reset.

**Hard forever (from Review):** 8d → 19d → 36d → 57d → 81d → 107d, with D
marching 4.75 → 9.28. Intervals keep growing but decelerate as D saturates —
no SM-2-style "ease hell" collapse.

**Easy forever:** 8d → 66d → 397d → 1,875d → 7,265d → 23,933d, D pinned at
1.00. Grows fast by design; capped at 36,500 d.

**Day boundary:** a card due 23:59 is not due at 23:58, is due at 23:59 and
any moment after — exact-timestamp comparison, no cliff, no double count.

**Overdue credit:** the same card graded Good exactly on due → 11 d; graded
Good 30 days late → **38 d** (S 10.97 vs 38.19). Lateness feeds the math.

**Cap:** S=99,999 pressed Good → `scheduled_days` prints **36,501** against
the 36,500 cap — interval is capped, the derived day-count is off by one at
the extreme. Cosmetic, but real.

## 4 · Button set and effects

Four grades — もう一度/Again, 難しい/Hard, ふつう/Good, 簡単/Easy — each
labeled with its true computed next interval (minutes or days read from the
actual `result` card, not an estimate).

| Button | Effect                                                                       |
| ------ | ---------------------------------------------------------------------------- |
| Again  | Lapse: S via `next_forget_stability`, lapses+1, relearning 10 min, D worsens |
| Hard   | Success with w₁₅ stability penalty; D worsens                                |
| Good   | Success; D nearly flat                                                       |
| Easy   | Success with w₁₆ stability bonus; D improves                                 |

Plus, outside the four grades: **rest** (suspend without grading — schedule
untouched, woken from the list), and **undo** (restores the exact prior stored
card object, never recomputed: `if (last.prev === undefined) delete
S.srs[key]; else S.srs[key] = last.prev`).

## 5 · Data model & content independence

The scheduler is fully content-blind. A card is keyed `"{type}:{id}"`
(`word:安堵`, `kanji:海`, `radical:氵`, `idiom:一期一会`) and stores only FSRS
state — the exact bytes:

```json
{
  "due": "2027-07-12T10:20:00.000Z",
  "stability": 131.76864467,
  "difficulty": 8.16659251,
  "elapsed_days": 76,
  "scheduled_days": 132,
  "reps": 12,
  "lapses": 1,
  "learning_steps": 0,
  "state": 2,
  "last_review": "2027-03-02T10:20:00.000Z"
}
```

Content is resolved at render time by `reviewBack(item)`, which switches on
the item type and reads the dictionary/kanji/radical/idiom records (or the
`S.deepWords` snapshot for 70k-tier words). Nothing content-shaped touches the
math.

**However — the target Japanese card-type taxonomy is not yet real.** Today
there is **one recognition card per item** (front: written form/glyph, or —
every other repetition of a word with corpus sentences — a cloze-blanked real
sentence; back: reading + senses). There are **no separate on-yomi/kun-yomi
cards, no production/reverse cards, and no authored AJATT sentence-mining card
type** — the cloze is derived automatically, not minable. The engine would
schedule such cards without modification (it is key-blind), but the card types
themselves do not exist.

## 6 · Queue & runtime behavior

```js
const NEW_PER_SESSION = 20;
function srsDueItems(now = new Date()) {
  const reviews = [],
    fresh = [];
  for (const item of S.taken) {
    if (S.suspended[key]) continue;
    const rec = S.srs[key];
    if (!rec) fresh.push(item);
    else if (new Date(rec.due) <= now) reviews.push(item);
  }
  return [...reviews, ...fresh.slice(0, NEW_PER_SESSION)];
}
```

- Due reviews first (in capture order), then up to 20 never-seen cards.
- The queue is **frozen at session start**.
- After days away, everything due enters one queue — no backlog cap, no
  penalty; lateness is credited (see §3).
- Scoped sessions (per-list) filter the same queue by key — same cards, same
  schedule, narrower door.
- The 集中道場 additionally cycles its pool to keep drilling when cards run
  dry; those extra passes are genuinely FSRS-rescheduled (early-review
  semantics: high R → small S gain, which the engine prices correctly).
- Leech: `lapses >= 6` → named 苦手 at session end, rest offered, never
  auto-suspended. Partial knowledge stays first-class.

## 7 · Verdict

**Is this a complete, correct, production-ready SRS engine? — Partially.**

### Genuinely correct and proven above

- FSRS-6 scheduling mathematics: pinned weights, real learning/relearning
  steps, correct lapse / overdue / cap behavior — demonstrated numerically
  through the actual storage round-trip.
- Exact-state undo; suspend/leech handling; content-blind card model; honest
  button labels; whole-record export/import; storage that cannot silently
  destroy state (read-only quarantine, unknown-key preservation).

### Missing or wrong, precisely

1. **No durable per-review log.** Only the in-session `rv.history` (discarded
   at session end) and a daily aggregate `{n, again}` survive. Without a
   persisted log of (card, rating, timestamp, elapsed, latency) the FSRS
   optimizer can never personalize the weights to this learner, history
   cannot be audited, and state cannot be rebuilt after a bug. **The single
   biggest gap for trusting the system with years of study.**
2. **Learning steps don't reinsert within a session.** Press Again and the
   card's 1-minute step matures, but the frozen queue never shows it again
   that session — in plain review the 1m/10m steps effectively span
   _sessions_, not minutes. Anki reinserts learning cards into the live
   queue. (The dojo's cycling pool masks this; plain review has it.)
3. **New-card pacing is per-session (20), not per-day.** Three sessions in a
   day can introduce 60 new cards. No daily cap exists.
4. **Fuzz is disabled**, so a batch of cards captured together stays
   synchronized forever — same-day due-pile clumping, the thing fuzz exists
   to prevent.
5. **One card type per item** — no on/kun split, no production direction, no
   authored sentence cards (§5).
6. Parameters are fixed defaults — fine to start (FSRS defaults are fit on
   large populations), but personalization is impossible until (1) exists.
7. Cosmetic: `scheduled_days` 36,501 at the 36,500 cap; undo does not survive
   a reload.

### Order of repair before trusting it with real long-term data

1. Append-only persisted review log (also the foundation the
   conversation-graph / adaptive-layer vision needs).
2. Learning-card reinsertion into the live queue.
3. True daily new-card cap.
4. Enable fuzz.
5. The Japanese card-type taxonomy as a deliberate design round with the
   operator.

None of these change the core math, which holds up.

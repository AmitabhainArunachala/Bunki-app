## Test and release bar

Automated users must operate the actual app and check persisted results across
onboarding, reading/listening, lookup, writing, tutor, capture/review, exams,
sync and recovery. Include beginner/intermediate/advanced fixtures, account
changes, concurrent offline devices, malformed imports, expired source access,
slow/failed providers, cancellation, partial updates and lost connectivity.

Review rendered phone and desktop states: typography, furigana and text
selection, keyboard/focus/Back behavior, touch targets, contrast, screen reader
and reduced motion, plus loading, empty and error states. Establish measured
responsiveness budgets on the supported real devices.

Release requires no known unresolved P0/P1 or acceptance-blocking defect,
passing applicable repository gates and the no-mistakes AXI delivery gate.
Lower-severity release exceptions need an explicit operator decision. Do not
claim unrun gates passed or universal freedom from undiscovered bugs.

The signed iPhone seven-day acceptance, daily installed-Mac handoffs, offline
activity, complete restore and voluntary continued use on day eight remain
required. Simulators and stubbed providers do not establish physical-device,
Japanese/editorial or real-provider quality.

## Build and evidence

`npm run bunki:web:dev` serves the actual Corridor. Build with
`node scripts/build-corridor-site.mjs --out /absolute/new/site-directory`.
The builder refuses existing destinations and in-checkout output, checks
runtime syntax, preserves the asset hierarchy and writes `build-identity.json`
with source revision, dirty-state disclosure and artifact file digests.
Shared reading, feed, assessment and browser record modules are compiled with the repository's pinned
compiler, recorded with their source inputs, and verified with every required
runtime asset. Development and browser verifiers use this prepared artifact.
The standalone builder also writes a fresh external artifact rather than
overwriting the historical source copy.

Set `KAIRO_SITE_DIR` to that staged directory when running browser verifiers.
An explicit `KAIRO_ARTIFACT_SHA256` pins a previously built candidate by all its
asset bytes and records that current source was not compared. This supports
parallel source work; publication still requires the clean source/artifact
verification in the release runner.
Reference corpus/history fixtures remain source-relative; runtime requests use
the packaged site. Send runtime output to `~/.dharma/` locally or the CI artifact
directory. No generated report belongs in a source commit.

Playwright is pinned to 1.63.0; both Chromium and WebKit reader/source journeys
are required. The previous 1.56.0 WebKit engine had a reproducible upstream
reload crash; the same reader artifact passed on WebKit 26.6 without an app
workaround. Browser simulation remains distinct from physical iPhone acceptance.

browser-context offline mode; WebKit uses an HTTPS server disconnected after

test. Each required practice receipt names its engine, mechanism and verified

# Bunki / KAIRO 1.1.0

Planned release date: 2026-10-13 (Asia/Tokyo). Publication is established by the GitHub Release and live build identity.

## Changes

- **Bug reports now reach GitHub and get fixed.** Until now the bug button
  saved reports only on the phone. The published app had no report service, so
  nothing was sent and nobody saw the reports.
- **The report relay.** A small Cloudflare Worker (`services/report-relay/`)
  receives each report from the app. It files the report as a GitHub issue,
  with your words, what you expected, the app version, the screen, the content,
  the language and your screenshots. You tap **Send report**; there is no
  GitHub page and no sign-in. A device is set up once with one link.
- **Reports show their progress.** Each report links to its issue and shows
  its status: received, being fixed, needs your answer, ready for review, or
  closed. The fixer's comments appear on the report. Your replies, and
  **Still happening**, go back to the issue and hand the report back to the
  fixer.
- **Earlier reports are sent too.** Reports saved before a device was set up,
  including ones saved by 1.0.x, are sent automatically once it is.
- **Without the relay set up,** a device still files reports. **Send to
  GitHub** opens a prefilled issue for you to submit, and **My reports** offers
  **Send to GitHub** and **Copy report text**. The sheet notes that issues in
  this repository are public.
- **The fixer.** A scheduled fixer agent checks reports with the
  `kairo-report` label every hour. It reproduces each problem and opens a pull
  request with the fix and a test. That pull request runs the full release
  checks, and the fix reaches the phone after it is merged and released. The
  pipeline and the fixer's procedure are in `docs/operator/BUG_REPORTS.md`.

## Data and compatibility

No learner-data, card-ID, backup-format, storage-key or FSRS change. Reports
keep their existing on-device store (`bunki-maintenance-reports-v1`). A saved
report gains only an optional `github_opened_at` time, which 1.0.x ignores.
The relay address and key are kept per device in `kairo-report-relay-v1`.
Learner-data epoch stays 1 with no migration, and rolling back to 1.0.1 is
compatible. The scheduler remains FSRS-6 through ts-fsrs 5.4.1 with
`bunki-fsrs6-r090-defaults-v1`.

Issues and their screenshots are public in this repository. A report contains
only what you write and the screenshots you choose, plus the listed screen
details.

## Verification

- **`report-relay` gate:** the relay's unit tests, run against a mock GitHub
  API and in-memory storage. They cover:
  - the key gate;
  - the labelled issue with screenshots;
  - receipt digests over the exact request bytes;
  - idempotent retries, and conflicts for changed payloads;
  - input validation;
  - GitHub outages;
  - status and comment views, replies and reopening, and the fixer labels
    they clear;
  - per-device lists;
  - CORS.
- **`report-delivery` gate:** runs the built app in Chromium and WebKit.
  - It uses a local relay against the mock GitHub API and a stubbed github.com.
  - For the relay, it covers the setup link, the automatic sending of an
    earlier report, a report with a screenshot becoming a linked issue, the
    fixer's status and comment appearing, and a reply becoming a comment.
  - For the prefilled-issue fallback, it covers the one-tap issue, long
    reports, blocked windows, Copy report text, the privacy note, and waiting
    for the service probe.
- **Workers runtime:** the Worker also ran in the Workers runtime
  (`wrangler dev --local`). There it answered config, session, filing with a
  screenshot, image serving and listing.

The live relay runs only after its one-time Cloudflare and GitHub setup
(`services/report-relay/README.md`). Opening GitHub from the home-screen app,
and the relay on a physical iPhone, have not been tested on a real device.

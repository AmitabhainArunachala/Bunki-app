## Key Question 1: Current model lineup, context windows, output limits, prices, and which tier fits which tutoring job

### Takeaway
Four current tiers are live on the Claude API: Fable 5.1 ($10/$50 per MTok, 1M ctx, 128K out), Opus 5.5 ($4/$20, 1M/128K, launched 2026-09-22), Sonnet 5 ($2/$10, 1M/128K, now permanent pricing), and Haiku 4.5 ($1/$5, 200K/64K). For a tutor: Sonnet 5 or Opus 5.5 for the interactive chat turn, Fable 5.1 (or Opus 5.5 at `xhigh`) for deep diagnosis, and Haiku 4.5 / Sonnet 5 via the Batch API for bulk mining.

### Inferences
- Interactive tutoring turn (latency-sensitive, many per day): Sonnet 5 ($2/$10, "Fast", 1M ctx, 1024-token cache minimum) is the price/latency sweet spot; Opus 5.5 at `low`/`medium` effort ($4/$20, cache reads $0.20) is the upgrade path with nearly identical cache-read cost per token as Sonnet 5.
- Deep diagnosis (weekly learner-model rebuild, error analysis over a day's transcript): Opus 5.5 at `xhigh`/`max` or Fable 5.1; Fable 5.1's $0.25 cache reads make repeated passes over a large learner dossier cheap, but its $50 output and 30-day-retention requirement matter.
- Bulk mining / reading generation: Haiku 4.5 or Sonnet 5 through the Batch API ($0.50/$2.50 and $1/$5 per MTok respectively). Note Haiku 4.5's 4096-token cache minimum and lack of `effort`/adaptive thinking.
- Japanese text costs more tokens on the 4.7+ tokenizer (approx. 30% more than Sonnet 4.6-era); budget with `count_tokens` on actual Japanese samples rather than English rules of thumb.

### Gaps
- No Japanese-specific tokens-per-character figure is published; the "555k words per 1M tokens" figure is English-centric. Measure with `/v1/messages/count_tokens`.
- Haiku 4.5's successor: no Haiku 5 appears in the docs as of 2026-09-28; Haiku 4.5's retirement floor is 2026-10-15, so a replacement may be imminent but is unconfirmed.

## Key Question 2: Tool use, agentic loops, tool_choice, client vs server tools, Tool Runner, computer use, and "tutor proposes a card / opens a passage" as tools

### Takeaway
Tools are ordinary JSON-schema functions on `POST /v1/messages`; client tools (your card/passage actions) run in your app, server tools (web search, web fetch, code execution, tool search, advisor) run on Anthropic's side. Parallel tool calls are on by default, `strict: true` guarantees schema-valid arguments, and forced `tool_choice` is gone on Fable 5.1 / Opus 5.5, so "propose a card" should be an `auto`-chosen strict tool plus a prompt instruction, not a forced call.

### Cited Findings
- Where tools run: "Client tools (including user-defined tools and tools with Anthropic-defined schemas, such as `bash` and `text_editor`) run in your application. Claude responds with `stop_reason: "tool_use"` and one or more `tool_use` blocks. Your code executes the operation and sends back a `tool_result`. Server tools (such as `web_search`, `web_fetch`, `code_execution`, and `tool_search`) run on Anthropic's infrastructure". — [Tool use overview](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)
- `tool_choice`: default `{"type":"auto"}`; `{"type":"auto","disable_parallel_tool_use":true}` asks for at most one call per turn; the trigger boundary is steerable via system prompt ("Always call a tool first before responding."). — [Tool use overview](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)
- Forced tool use removed on newest models: "Claude Fable 5.1, Claude Mythos 5.1, and Claude Opus 5.5 reject forced tool use: `{"type": "any"}` and `{"type": "tool", "name": ...}` return a 400 ... on `count_tokens` and Batches too ... Use `{"type": "auto"}` and state the expectation in the prompt ... `strict: true` on the tool keeps the schema-valid-arguments guarantee `any` gave you - or structured outputs (`output_config.format`) when the forced call only existed to extract JSON." — [claude-api skill shared/tool-use-concepts.md, local]; release note 2026-09-01 "Strict tool use requirement" — [Release notes](https://platform.claude.com/docs/en/release-notes/overview)
- Strict tool use: "Add `strict: true` to your custom tool definitions to ensure Claude's tool calls always match your schema exactly." Schema must have `additionalProperties: false` and `required` (skill). — [Tool use overview](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview); [claude-api skill]
- Parallel tool use is default-on: "one assistant message may contain multiple `tool_use` blocks. Execute them concurrently, then return all `tool_result` blocks in a single user message - splitting them across multiple messages silently trains Claude to stop making parallel calls." — [claude-api skill SKILL.md, local]
- Tool-use system-prompt overhead (auto/none): Opus 5.5 286 tokens, Opus 5 286, Opus 4.8 290, Sonnet 5 354, Haiku 4.5 496; tool definitions, `tool_use` and `tool_result` blocks are billed as normal input tokens. — [Pricing, tool use](https://platform.claude.com/docs/en/about-claude/pricing)
- Tool Runner (SDK beta helper) drives the request -> execute -> loop for tools you define: Python `@beta_tool` + `client.beta.messages.tool_runner(...)`, TypeScript `betaZodTool` + `client.beta.messages.toolRunner(...)`, with per-turn hooks for approval gates, logging, result modification, retries, streaming, compaction; available in all seven SDKs. — [claude-api skill SKILL.md, local]; [Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview) (confirms "the client SDK's beta tool runner")
- Fine-grained tool streaming is GA (no beta): set `eager_input_streaming: true` per tool on a streaming request so large tool inputs stream; client must then validate parsed input against the schema and check `stop_reason` for `max_tokens`/`refusal` before executing. — [claude-api skill SKILL.md, local]; [Streaming](https://platform.claude.com/docs/en/build-with-claude/streaming) ("Enable it per tool with `eager_input_streaming`")
- Server tools and type strings: web search `web_search_20260209` ($10 per 1,000 searches), web fetch `web_fetch_20260209` (no extra charge beyond tokens; `max_content_tokens` guard), code execution `code_execution_20260521` (free when combined with web search/fetch; otherwise 1,550 free container-hours/org/month then $0.05/hour, 5-minute minimum), tool search `tool_search_tool_regex_20251119` / `_bm25_20251119`, advisor tool (beta). — [Pricing](https://platform.claude.com/docs/en/about-claude/pricing); [claude-api skill SKILL.md]
- Programmatic tool calling (GA): custom tool with `"allowed_callers": ["code_execution_20260120"]` lets Claude call your tool from inside code; not compatible with `strict: true`, `disable_parallel_tool_use`, forced `tool_choice`, or MCP tools. — [claude-api skill SKILL.md, local]
- Computer use is out of beta as `computer_toolset_20260801` (2026-08-19); declaring it adds about 4,500 input tokens per request; browser use tool `browser_toolset_20260801` adds about 6,600 tokens; screenshots billed as image input. Opus 5.5 accepts only the toolset form. — [Release notes 2026-08-19](https://platform.claude.com/docs/en/release-notes/overview); [Pricing](https://platform.claude.com/docs/en/about-claude/pricing)
- Anthropic-schema client tools (you execute, Anthropic trains the schema): memory `memory_20250818`, bash `bash_20250124` (adds 325 tokens on Opus 5/4.8/4.7), text editor `text_editor_20250728` (700 tokens), computer, browser. — [Tool use overview](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview); [Pricing](https://platform.claude.com/docs/en/about-claude/pricing)
- Stop reasons: `end_turn`, `max_tokens`, `stop_sequence`, `tool_use`, `pause_turn` (resume server-tool loops), `refusal` (check `stop_details`). — [claude-api skill typescript README, local]
- Mid-conversation tool changes (beta `mid-conversation-tool-changes-2026-07-01`, and "inline tools" beta `inline-tools-2026-09-15` per release note 2026-09-22) let you add/remove tools without invalidating the cached prefix on Opus 5/5.5/4.8 and Fable 5/5.1 (not Sonnet 5). — [claude-api skill shared/prompt-caching.md]; [Release notes](https://platform.claude.com/docs/en/release-notes/overview)
- Tool search: "never defer everything" - at least one non-deferred tool or the API returns 400. — [claude-api skill SKILL.md]

### Inferences
- Model "the tutor proposes a card" and "open passage" as client tools with `strict: true` and small schemas (e.g. `propose_card{front, back, reading, example_sentence, tags[]}` and `open_passage{passage_id, highlight_span}`); keep the tool list byte-stable and sorted so the tools prefix caches; steer with a system-prompt sentence rather than `tool_choice: any`, which now 400s on Fable 5.1/Opus 5.5.
- Return all tool results from one assistant turn in a single user message, or Claude stops issuing parallel proposals (multiple cards in one turn).
- Because forced tool use is gone on the newest models, extraction jobs ("give me exactly one JSON object") should use structured outputs (`output_config.format`), not a forced tool.

### Gaps
- Docs do not state a hard cap on the number of tools per request; the tool-search tool exists for "thousands of tools" but no numeric limit was found.

## Key Question 3: Structured outputs and reliable extraction of typed learner observations

### Takeaway
Yes: strict JSON-schema output is GA on every current model via `output_config: {format: {type: "json_schema", schema: ...}}` (grammar-constrained sampling) and `strict: true` on tools; the SDKs' `messages.parse()` validates against your Pydantic/Zod type. Constraints: no recursive schemas, no numeric/length constraints (SDK strips them and validates client-side), `additionalProperties: false` required, 24-hour grammar cache, and structured outputs are incompatible with citations.

### Cited Findings
- Mechanism: `output_config.format` with `{"type":"json_schema","schema":{...}}` "constrains Claude's responses using grammar-constrained sampling ... Returns valid JSON matching your schema in the response's text content block ... No parsing errors or schema violations". — [Structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)
- Supported models: Opus 5.5, 5, 4.8, 4.7, 4.6, 4.5; Sonnet 5, 4.6, 4.5; Haiku 4.5; Fable 5.1, 5; Mythos 5.1, 5; GA on Claude API, Claude Platform on AWS, Bedrock, Google Cloud, Foundry. — [Structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)
- Schema support: object/array/string/integer/number/boolean/null; `enum` (strings, numbers, bools, nulls only); `const`, `anyOf`, `allOf` (with limitations); `$ref`/`$defs` (no external refs); string formats `date-time`, `time`, `date`, `duration`, `email`, `hostname`, `uri`, `ipv4`, `ipv6`, `uuid`; array `minItems` only 0 or 1; `required` and `additionalProperties: false` required for objects. Not supported: recursive schemas, `minimum`/`maximum`/`multipleOf`, `minLength`/`maxLength`, complex types in enums, external `$ref`, limited nesting depth. — [Structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)
- SDK transformation: Python/TypeScript/Ruby/PHP SDKs strip unsupported constraints, append them to descriptions, add `additionalProperties: false`, filter formats, and "Validate responses against original schema (with all constraints)". — [Structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)
- Grammar compilation: "First request with a schema has additional latency due to grammar compilation"; "Compiled grammars are cached for 24 hours from last use"; cache invalidated by schema structure or tool-set changes, not by `name`/`description` edits. — [Structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)
- Costs and cache interaction: an additional system prompt is injected (more input tokens); "Changing `output_config.format` invalidates prompt cache for that conversation thread". — [Structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)
- Incompatibilities: citations (400), prefill (already removed on 4.6+ models), works with streaming but JSON must be accumulated before parsing; `max_tokens: 0` pre-warm cannot be combined with `output_config.format`. — [Structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs); [claude-api skill shared/prompt-caching.md]
- Parameter history: `output_format` deprecated; moved to `output_config.format` and GA on 2026-01-29; no beta header. — [Release notes 2026-01-29](https://platform.claude.com/docs/en/release-notes/overview)
- ZDR/HIPAA: structured outputs are "Yes (qualified)" for ZDR - "Only the JSON schema is cached, for up to 24 hours since last use"; do not put PHI/personal data in schema property names, enums, consts or patterns because cached grammars are stored separately from message content. — [API and data retention](https://platform.claude.com/docs/en/manage-claude/api-and-data-retention)
- Recommended SDK path: `client.messages.parse()` "automatically validates responses against your schema". — [claude-api skill SKILL.md, local]

### Inferences
- For typed learner observations (e.g. `{skill_id, evidence_span, error_type: enum, confidence: number, next_action: enum}`), define one frozen schema per job so the grammar stays cached; encode confidence as an enum or `number` without `minimum`/`maximum` (enforce range client-side via the SDK's original-schema validation); avoid recursion (flatten nested observation trees into arrays with parent ids).
- Run extraction as a separate call from the conversational turn (different `output_config.format` on the chat route would invalidate the chat cache); batch the day's extractions through the Batch API at 50% off.

### Gaps
- The exact maximum nesting depth and schema size limits are not stated numerically on the docs page fetched ("Limited depth for nested object/array structures").

## Key Question 4: Prompt caching - minimums, TTLs, multipliers, and a worked estimate for a ~6k-token system prompt + learner model at 40 turns/day

### Takeaway
Caching is a byte-exact prefix match with 4 breakpoints, 5-minute (1.25x write) or 1-hour (2x write) TTL, reads at 0.1x (0.05x on Opus 5.5, 0.025x on Fable 5.1); minimum cacheable prefix is 512 tokens on Opus 5/5.5 and Fable 5/5.1, 1024 on Sonnet 5 and Opus 4.8, 4096 on Haiku 4.5. A 6k-token learner context caches on every current model; at 40 turns/day in a few sessions, caching cuts the prefix cost by roughly 84% and total daily cost per learner to about $0.25 (Sonnet 5), $0.45 (Opus 5.5), $0.12 (Haiku 4.5), $1.07 (Fable 5.1) under the assumptions below.

### Cited Findings
- Multipliers: "5-minute cache write 1.25x base input price ... 1-hour cache write 2x ... Cache read (hit) 0.1x base input price (0.025x on Claude Fable 5.1 and Claude Mythos 5.1; 0.05x on Claude Opus 5.5)"; "caching pays off after one cache read for the 5-minute duration (1.25x write), or after two cache reads for the 1-hour duration (2x write)"; multipliers "stack with other pricing modifiers, including the Batch API discount and data residency." — [Pricing, prompt caching](https://platform.claude.com/docs/en/about-claude/pricing)
- Minimum cacheable prompt length: Fable 5.1, Mythos 5.1, Opus 5.5, Opus 5, Fable 5, Mythos 5: 512 tokens; Opus 4.8, Sonnet 5, Sonnet 4.6, Sonnet 4.5, Opus 4.1, Opus 4, Sonnet 4: 1,024; Opus 4.7, Mythos Preview, Haiku 3.5: 2,048; Opus 4.6, Opus 4.5, Haiku 4.5: 4,096. Shorter prompts "cannot be cached; no error returned, just processed without caching". — [Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)
- TTL and syntax: `"cache_control": {"type": "ephemeral"}` (5 min default) or `{"type":"ephemeral","ttl":"1h"}`; max 4 breakpoints per request; automatic caching (top-level `cache_control`) uses one slot; 20-block lookback window; "Cache lifetime measurement: From request start, not end". — [Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)
- Cache isolation: per workspace on the Claude API, Claude Platform on AWS and Foundry; per organization on Bedrock and Google Cloud; never across organizations. — [Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)
- Invalidation hierarchy (tools -> system -> messages): tool-definition or model changes invalidate everything; system-prompt content invalidates system+messages; `tool_choice` and images invalidate messages only; thinking/effort changes invalidate the messages cache and are model-specific for tools/system. Mid-conversation `role: "system"` messages (Opus 5/5.5/4.8, Fable 5/5.1; not Sonnet 5; no beta) preserve the cached prefix. Per-message effort (`mid-conversation-output-config-2026-07-01`) avoids the effort-change invalidation on Fable 5.1 / Opus 5 / Opus 5.5. — [Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching); [claude-api skill shared/prompt-caching.md, local]
- Automatic caching launched 2026-02-19; cache diagnostics (`diagnostics.previous_message_id`) went GA with no beta header on 2026-09-23. — [Release notes](https://platform.claude.com/docs/en/release-notes/overview)
- Cache reads do not count toward ITPM rate limits on current models: "only uncached input tokens count toward your ITPM rate limits"; `cache_read_input_tokens` do not count (Haiku 3.5 is the only exception). — [Rate limits](https://platform.claude.com/docs/en/api/rate-limits)
- Keep-alive trick: `max_tokens: 0` re-sends the request to refresh the entry, billing only a cache read; rejected with `stream: true`, `output_config.format`, forced `tool_choice`, or inside a batch. On Fable 5.1 (0.025x reads) this is usually cheaper than the 1-hour TTL. — [claude-api skill shared/prompt-caching.md, local]
- Batch + cache: "cache hits are provided on a best-effort basis. Users typically experience cache hit rates ranging from 30% to 98%"; use the 1-hour TTL for batches. — [Batch processing](https://platform.claude.com/docs/en/build-with-claude/batch-processing)

### Inferences
Worked estimate (my arithmetic from the cited prices; assumptions stated):
- Assumptions: frozen prefix (tools + system + learner model) = 6,000 tokens, placed before the last breakpoint; each turn adds ~150 tokens of new user input and produces ~400 output tokens (excludes adaptive-thinking tokens, which are billed as output and can dominate at high effort); 40 turns/day happen in 2 sessions of 20 turns with turns < 5 min apart, so each session is 1 cache write (5m TTL) + 19 reads. Per-turn conversation history growth is ignored (with automatic caching the history is also read from cache and only the delta is written, so this understates savings slightly).
- Daily prefix tokens: 40 x 6,000 = 240,000. Cached: 2 x 6,000 = 12,000 written at 1.25x; 38 x 6,000 = 228,000 read.
- Sonnet 5 ($2 in, $2.50 write, $0.20 read, $10 out): uncached input $0.48 + user text $0.012 + output $0.16 = $0.65/day. Cached: writes $0.03 + reads $0.046 + user text $0.012 + output $0.16 = $0.25/day (about $7.50/learner/month vs $19.50 uncached). Prefix cost falls from $0.48 to $0.076 (-84%).
- Opus 5.5 ($4 / $5 / $0.20 / $20): uncached $0.96 + $0.024 + $0.32 = $1.30/day; cached $0.06 + $0.046 + $0.024 + $0.32 = $0.45/day (~$13.50/month). Note the cache-read price equals Sonnet 5's, so a well-cached Opus 5.5 tutor is mostly paying for output.
- Haiku 4.5 ($1 / $1.25 / $0.10 / $5): uncached $0.24 + $0.006 + $0.08 = $0.33/day; cached $0.015 + $0.023 + $0.006 + $0.08 = $0.12/day (~$3.70/month). The 6k prefix clears Haiku's 4,096-token minimum; a prefix under 4,096 tokens would silently not cache on Haiku.
- Fable 5.1 ($10 / $12.50 / $0.25 / $50): uncached $2.40 + $0.06 + $0.80 = $3.26/day; cached $0.15 + $0.057 + $0.06 + $0.80 = $1.07/day (~$32/month); output tokens are ~75% of the cached bill.
- Worst case: if the 40 turns were each >5 minutes apart with the 5-minute TTL, every turn would be a 1.25x write (Sonnet 5: $0.60/day for the prefix, worse than uncached). For a learner who replies every 5-60 minutes, use `ttl: "1h"` (2x write, pays off after two reads) or, on Fable 5.1, a `max_tokens: 0` keep-alive.
- Design implications: put the per-learner model after the global system prompt with two explicit breakpoints (global prefix shared by all learners; learner block per session), keep dates/session ids out of the prefix (inject via a mid-conversation `system` message on Opus/Fable, or a user-turn block on Sonnet 5), never vary `effort` or the tool list per turn, and verify with `usage.cache_read_input_tokens`.

### Gaps
- Thinking-token volume per tutoring turn is unknown and model/effort dependent; it is billed as output and is likely the largest variable in the real bill. Measure `usage.output_tokens_details.thinking_tokens` (added 2026-05-27) on a sample.

## Key Question 5: Batch API for nightly jobs

### Takeaway
The Message Batches API gives 50% off every token (stacking with cache discounts), accepts up to 100,000 requests or 256 MB per batch, usually finishes within an hour with a hard 24-hour expiry, keeps results 29 days, supports nearly all Messages features (tools, thinking, structured outputs, PDFs, caching) but not streaming, fast mode, or `max_tokens: 0`, and is not ZDR-eligible.

### Cited Findings
- "most batches finishing in less than 1 hour while reducing costs by 50%"; "A Message Batch is limited to either 100,000 Message requests or 256 MB in size, whichever is reached first"; "You can access batch results when all messages have completed or after 24 hours, whichever comes first. Batches expire if processing does not complete within 24 hours"; "Batch results are available for 29 days after creation". — [Batch processing](https://platform.claude.com/docs/en/build-with-claude/batch-processing)
- Unsupported params: `stream`, `speed`, `max_tokens: 0`; otherwise "supports nearly all features available in the Messages API, including most beta features". Expired requests are not billed. — [Batch processing](https://platform.claude.com/docs/en/build-with-claude/batch-processing)
- Batch prices per MTok (input/output): Fable 5.1 $5/$25; Opus 5.5 $2/$10; Opus 5 and 4.x $2.50/$12.50; Sonnet 5 $1/$5; Sonnet 4.6/4.5 $1.50/$7.50; Haiku 4.5 $0.50/$2.50. — [Pricing, batch](https://platform.claude.com/docs/en/about-claude/pricing)
- Batch rate limits (shared across models): Start tier 1,000 RPM / 200,000 queued requests / 100,000 per batch; Build 2,000 / 300,000 / 100,000; Scale 4,000 / 500,000 / 100,000. — [Rate limits](https://platform.claude.com/docs/en/api/rate-limits)
- Extended output: up to 300k output tokens per batched request with beta `output-300k-2026-03-24` (Claude API and Claude Platform on AWS only); "A single 300k-token generation can take over an hour". — [Batch processing](https://platform.claude.com/docs/en/build-with-claude/batch-processing); [Models overview](https://platform.claude.com/docs/en/about-claude/models/overview)
- Retention: "Batch processing stores request and response data for up to 29 days after batch creation. You can delete a message batch at any time after processing"; not ZDR- or HIPAA-eligible ("29-day retention; async storage required"). — [Batch processing](https://platform.claude.com/docs/en/build-with-claude/batch-processing); [API and data retention](https://platform.claude.com/docs/en/manage-claude/api-and-data-retention)

- Results arrive in any order; key by `custom_id`; SDK: `client.messages.batches.create(...)`, poll `processing_status == "ended"`, stream `.results(id)`. — [claude-api skill SKILL.md, local]
- `inference_geo` can be set per request inside a batch. — [Data residency](https://platform.claude.com/docs/en/manage-claude/data-residency)

### Inferences
- Nightly mining of a day's exchanges (extract observations with structured outputs) and generating graded readings fit the batch envelope: submit after the day ends, expect results within ~1 hour, well inside a 24-hour window; use the 1-hour cache TTL on a shared "mining rubric" prefix so many requests share it.
- Because batch requests are single-shot (no tool loop), flatten "read transcript -> emit JSON" into one request each; tool loops that need results back cannot run inside a batch.

### Gaps
- No documented SLA beyond "most batches complete within 1 hour"; heavy demand "may" push requests to the 24-hour expiry.

## Key Question 6: Agent SDK, Managed Agents, MCP - what they offer a tutor needing memory, tools, long sessions; what runs where; costs

### Takeaway
Three distinct surfaces: (1) Claude API + Tool Runner (you host the loop; cheapest, ZDR-eligible); (2) Claude Agent SDK (Claude Code as a Python/TypeScript library with built-in file/bash/web tools, sessions, hooks, MCP; you host; API-key auth only, claude.ai login not allowed for third-party products); (3) Managed Agents (beta `managed-agents-2026-04-01`; Anthropic hosts the loop and a per-session sandbox; $0.08 per session-hour running time plus normal tokens; memory stores, vaults, scheduled deployments, outcomes; not ZDR/HIPAA-eligible). ### Inferences
- For a consumer tutor with many concurrent learners and short interactive turns, Claude API + Tool Runner (or a hand-written loop) on your own servers is the natural fit: no per-session-hour charge, ZDR-eligible, and you own the learner store. - MCP is useful for exposing the tutor's own card/passage/SRS services as a remote server that both the Messages API (via connector) and Managed Agents can call, but it costs ZDR eligibility on the connector path.

## Key Question 8: Privacy - retention defaults, ZDR, HIPAA/SOC 2, EU/Japan residency

### Takeaway
On the Claude API conversation content "is not retained by default" and is never used for training without permission, with two formal arrangements: ZDR (org- or workspace-level) and HIPAA readiness (self-serve standard BAA in the Console). ## Key Question 9: Rate limits, streaming, thinking/effort controls, and running Claude from a browser or mobile app safely

### Takeaway
Rate limits are per-model, per-org token buckets with three self-serve tiers (Start/Build/Scale) capped at $500 / $1,000 / $200,000 monthly spend; Sonnet 5, Opus 5.5 and Haiku 4.5 get 1,000-10,000 RPM and 2M-10M ITPM, with cache reads not counting toward ITPM. Streaming is SSE and required by the SDKs for large outputs; thinking is adaptive and steered by `output_config.effort` (`low`..`max`). Browser/mobile clients should never hold an API key: the SDK blocks browser use unless `dangerouslyAllowBrowser: true`, which sends the `anthropic-dangerous-direct-browser-access: true` header; the documented safe pattern is a server-side proxy/gateway that holds the key (or per-workspace/personal keys with expiry).

### Cited Findings
- Spend caps: Start $500, Build $1,000, Scale $200,000 per month; Custom tier has none; at the cap requests return 429 `enforced_spend_limit_reached` until 00:00 UTC on the 1st. New orgs "may start in the Evaluation tier, with limits below the standard limits". — [Rate limits](https://platform.claude.com/docs/en/api/rate-limits)
- Per-model limits (RPM / ITPM / OTPM): Start tier - Fable 5.x 1,000 / 500,000 / 100,000; Opus 5.5, Opus 5, Opus 4.x, Sonnet 5, Sonnet 4.x, Haiku 4.5 each 1,000 / 2,000,000 / 400,000. ### Inferences
- A mobile/web tutor should route every call through your backend (the backend holds the key, adds `cache_control`, enforces per-learner quotas, and re-streams SSE to the client); `dangerouslyAllowBrowser` plus the direct-browser-access header is only defensible for internal tools or a local prototype where the user supplies their own key.
- Per-learner throughput is not the constraint; org-level ITPM/OTPM is. At Start tier, Sonnet 5's 400,000 OTPM at ~400 output tokens/turn supports about 1,000 tutoring turns per minute org-wide; caching keeps the 6k prefix out of ITPM entirely.
- For a chat UI, stream with `thinking: {type:"adaptive", display:"summarized"}` or the default omitted mode plus a "thinking..." indicator, and pin `effort` per route (`low`/`medium` for chat turns, `xhigh`/`max` for diagnosis) rather than per request to avoid cache invalidation.

### Gaps
- The official docs page that documents the `anthropic-dangerous-direct-browser-access` header (CORS section) was not located; the header name and behaviour are confirmed only from the SDK source.
- Evaluation-tier starting limits for brand-new organizations are not published numerically.
